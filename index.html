1Introduction

A blockchain is a peer-to-peer distributed ledger that is cryptographically secure, append-only, immutable and updatable only through consensus or agreement among peers. It runs as a layer on top of the Internet, just as SMTP, HTTP or FTP run on top of TCP/IP.

From a business point of view it is a platform where peers exchange value using transactions without the need for a central trusted arbitrator. This question has two parts:

  • Part (i) – the features that make a blockchain trustworthy.
  • Part (ii) – the tiers (generations) that show how blockchain usage evolved from currency to the whole of society.

Key point: Features answer "why can we trust it?"; tiers answer "what has it been used for, over time?"

2Content

PART (i) – FEATURES OF BLOCKCHAIN TECHNOLOGY

2.1 Distributed consensus

  • Enables a blockchain to present a single version of truth agreed upon by all parties without a central authority.
  • Achieved by algorithms such as PoW, PoS, PBFT.
  • Example: every Bitcoin node agrees on the same ordered list of transactions.

2.2 Transaction verification

  • Every transaction posted by a node is verified against predetermined rules (valid signature, sufficient balance, correct format).
  • Only valid transactions are selected for inclusion in a block → invalid or fraudulent transactions never reach the ledger.

2.3 Platform for smart contracts

  • A blockchain is a platform where programs run and execute business logic on behalf of users.
  • Smart contracts are automated, autonomous programs that reside on the blockchain and execute when certain conditions are met.
  • Available on Ethereum, Multichain, Hyperledger – not on Bitcoin (limited script).

2.4 Transferring value between peers

  • Value moves directly between users through tokens (tokens = carriers of value).
  • No bank or payment processor is needed.

2.5 Generating cryptocurrency

  • Optional feature, depends on the blockchain type.
  • Cryptocurrency is created as an incentive for miners who validate transactions and spend resources to secure the chain (e.g. Bitcoin block reward).

2.6 Smart property

  • A digital or physical asset is linked to the blockchain irrevocably, so it cannot be claimed by anyone else.
  • The owner has full control; the asset cannot be double-spent or double-owned.
  • Contrast: a digital music file can be copied endlessly, but on a blockchain nobody can claim it unless it is transferred.
  • Used in Digital Rights Management (DRM) and e-cash where double-spend detection is key.

2.7 Provider of security

  • Based on proven cryptography (hashing, public-key cryptography) → ensures integrity and availability of data.
  • Non-repudiation and authentication through private keys and digital signatures.
  • Confidentiality is generally NOT provided because of the transparency requirement – a major barrier for banks and industries that need privacy.

2.8 Immutability

  • Records once added cannot be changed.
  • Rolling back is theoretically possible but needs enormous computing power – an attacker would have to recompute PoW for the altered block and all blocks after it.
  • Hence records are practically immutable.

2.9 Uniqueness

  • Every transaction is unique and has not been spent already.
  • Key requirement for cryptocurrencies → double-spending detection and avoidance.

2.10 Additional characteristics

Characteristic Meaning
Decentralized No single owner; every node keeps a copy
Transparent / traceable Anyone can audit the history
Time-stamped Every block carries a timestamp
Pseudonymous Users act through addresses, not names
Highly available Thousands of replicas keep it running

Key point: Blockchain gives integrity, availability, authentication, non-repudiation – but not confidentiality by default.

PART (ii) – TIERS OF BLOCKCHAIN TECHNOLOGY

Blockchain is evolving, and this versioning shows the different tiers of evolution and usage. All platforms (with few exceptions) support these functionalities.

2.11 Blockchain 1.0 – Cryptocurrency

  • Introduced with the invention of Bitcoin (2009); used primarily for cryptocurrencies.
  • As Bitcoin was the first implementation of cryptocurrency, this generation includes only cryptographic currencies.
  • All alternative cryptocurrencies + Bitcoin fall into this tier.
  • Core applications: payments and money transfer.
  • Period: started 2009 (Bitcoin release) to early 2010.

2.12 Blockchain 2.0 – Financial services & smart contracts

  • Used by financial services and smart contracts.
  • Includes financial assets like derivatives, options, swaps and bonds.
  • Applications that go beyond currency, finance and markets are incorporated here.
  • Platforms: Ethereum, Hyperledger and newer blockchains.

2.13 Blockchain 3.0 – Beyond financial services

  • Implements applications beyond the financial industry: government, health, media, the arts and justice.
  • Again Ethereum, Hyperledger and newer smart-contract blockchains are part of this tier.
  • Emerged around 2012, when applications in many industries were researched.

2.14 Blockchain X.0 – Blockchain singularity (future vision)

  • One day there will be a public blockchain service available to anyone, just like the Google search engine.
  • Provides services for all realms of society.
  • A public, open distributed ledger with general-purpose rational agents (Machina economicus) running on the blockchain, making decisions and interacting with other intelligent autonomous agents on behalf of people.
  • Regulated by code instead of law or paper contracts.

1Introduction

Consensus is the process of agreement between distrusting nodes on the final state of data. Agreement between two nodes (client–server) is easy; agreement among many nodes – distributed consensus – is hard, especially when some nodes are faulty or Byzantine (malicious).

A consensus mechanism is a set of steps taken by all or most nodes to agree on a proposed state or value. Because blockchains differ (public vs private, small vs large, energy budget, speed), no single mechanism is best for all – the designer must evaluate the options and choose the most suitable one.

Key point: "Consensus is the backbone of a blockchain" – choose it according to the type of network and its requirements.

2Content

2.1 Requirements every consensus mechanism must satisfy

Requirement Meaning
Agreement All honest nodes decide on the same value
Termination All honest nodes terminate execution and eventually reach a decision
Validity The agreed value must be the same as the initial value proposed by at least one honest node
Fault tolerance Works even in the presence of faulty or malicious nodes
Integrity A node makes a decision only once in a single consensus cycle

2.2 Two broad categories

2.3 Proof-based mechanisms

a) Proof of Work (PoW)

  • Relies on proof that enough computational resources were spent before proposing a value.
  • Used in Bitcoin; the only algorithm proven astonishingly successful against Sybil attacks.
  • Drawback: very high energy consumption, slow (≈10 min blocks).

b) Proof of Stake (PoS)

  • A node that has enough stake (coins invested) proposes blocks; any attack would cost more than its benefit.
  • Introduced by Peercoin; planned for Ethereum (Casper).
  • Coin age = amount × time coins unspent; higher coin-age → higher chance to sign the next block.

c) Delegated Proof of Stake (DPoS)

  • Stakeholders vote to delegate validation to a few nodes (e.g. 101 delegates in Lisk); used in BitShares.

d) Proof of Elapsed Time (PoET)

  • By Intel; uses a Trusted Execution Environment (Intel SGX) to give each node a random guaranteed wait time; first to finish waiting becomes leader. Used in Hyperledger Sawtooth.

e) Deposit-based consensus – nodes place a security deposit before proposing a block (basis of Casper).

f) Proof of Importance – not only stake but also usage and movement of tokens to establish trust (used in NEM).

g) Reputation-based – leader elected on the basis of reputation built over time / votes.

h) Proof of Activity – PoW first stage + PoS remaining stages for energy efficiency; stakeholder chosen pseudo-randomly.

i) Proof of Capacity – uses hard-disk space instead of CPU ("hard-drive mining", BurstCoin).

j) Proof of Storage – outsourcing of storage; variants Proof of Replication, Data Possession, Space, Space-time.

k) Proof of Authority (PoA) – identity of validators is the stake; validators propose & validate blocks (Clique, Aura).

2.4 Byzantine fault tolerance-based mechanisms

a) PBFT (Practical Byzantine Fault Tolerance)

  • Achieves state-machine replication tolerant to Byzantine nodes.
  • Phases: request → pre-prepare → prepare → commit → reply; decision when a majority agrees.
  • Tolerates f faulty nodes out of 3f + 1 (standard result).

b) Federated Byzantine Agreement (FBA) – used in Stellar; each node trusts a group of public peers and propagates only transactions validated by the majority of trusted nodes.

c) Paxos / RAFT – leader-based; Paxos roles Proposer, Acceptor, Learner; RAFT states Follower, Candidate, Leader.

2.5 Comparison of major mechanisms

Mechanism Energy Speed / finality Scalability (nodes) Sybil resistance Best for
PoW Very high Slow, probabilistic Very high Excellent Open cryptocurrencies
PoS Low Faster High Good (stake) Public chains wanting efficiency
DPoS Low Fast Medium Voting High-throughput public chains

PBFT Low Immediate finality Low (tens of nodes) Membership Consortium (Fabric)
FBA Low Fast Medium Trusted quorums Payment networks (Stellar)

2.6 Decision process to determine the most suitable mechanism

Steps a designer follows:

  1. Identify the network type – public, private or consortium.
  2. Check trust assumptions – are participants anonymous, known, or fully trusted?
  3. Decide performance targets – transactions per second, finality time.
  4. Consider energy and hardware – mining farms? SGX processors? disk space?
  5. Check security threats – Sybil, 51 %, nothing-at-stake.
  6. Select and test the mechanism on a test network.

2.7 Example scenarios

Scenario Most suitable Reason
New public cryptocurrency PoW (or PoS) Open, Sybil-resistant
Energy-efficient public DApp platform PoS / DPoS No mining hardware race
Banks sharing a settlement ledger PBFT Known members, instant finality
Large enterprise network on Intel servers PoET Fair random leader, low energy
Private test network PoA Simple, fast

Key point (from slides): "Not all consensus mechanisms are suitable for all types of blockchains. In public permissionless blockchains it would make sense to use PoW instead of a basic agreement mechanism based on proof of authority."

3Conclusion / Summary
  • Consensus lets distrusting nodes agree on one ledger state while satisfying agreement, termination, validity, fault tolerance and integrity.
  • Proof-based (Nakamoto) algorithms – PoW, PoS, DPoS, PoET, PoA, etc. – suit open, large networks; BFT-based algorithms – PBFT, FBA, RAFT – suit permissioned networks needing speed and finality.
  • The most suitable mechanism is chosen by evaluating network openness, trust model, performance, energy and security threats: Public → PoW/PoS; Consortium → PBFT; Enterprise with SGX → PoET; Private → PoA/RAFT.

1Introduction

Consensus is the process of agreement between distrusting nodes on the final state of data. A consensus mechanism is a set of steps taken by all or most nodes to agree on a proposed value. Choosing the right one depends on the type of blockchain (public / permissioned), required speed, security, energy use and scalability.

2Content

Requirements of any consensus mechanism

  • Agreement – all honest nodes decide on the same value.
  • Termination – all honest nodes eventually reach a decision.
  • Validity – the agreed value was proposed by at least one honest node.
  • Fault tolerance – works in the presence of faulty/malicious nodes.
  • Integrity – a node decides only once per consensus cycle.

Two categories

  1. Proof-based / leader-based (Nakamoto consensus) – a leader is elected and proposes the final value. Used in decentralized, permissionless chains (Bitcoin, Ethereum). Scalable but slow.
  2. Byzantine-fault-tolerance based – traditional rounds of voting. Used in consortium/permissioned chains. Fast but not very scalable.

3Illustrate the elements in full ecosystem decentralization.16M
1Introduction

Blockchain itself is a distributed ledger that runs on top of conventional systems – servers, ISPs, centralized storage and identity providers. If only the ledger is decentralized but everything around it is centralized, the system still has central points of control and failure.

To achieve complete (full ecosystem) decentralization, the environment around the blockchain must also be decentralized. The elements to be decentralized are Storage, Communication and Computation, and at the top, the factors traditionally based on centralized paradigms – Identity and Wealth.

Key point: Full ecosystem decentralization = decentralized Storage + Communication + Computation + Identity/Wealth.

2Content

2.1 Storage

Problem

  • Data can be stored directly in a blockchain – that is decentralized – but blockchain is not suitable for large amounts of data by design.
  • It can store transactions with arbitrary data but not images or large blobs, unlike traditional databases.

Solution – Distributed Hash Tables (DHTs)

  • Originally used in P2P file sharing: BitTorrent, Napster, Kazaa, Gnutella; research made popular by CAN, Chord, Pastry, Tapestry.
  • BitTorrent is scalable and fast, but there is no incentive for users to keep files permanently; if nodes leave, the data is lost.
  • Two main requirements: high availability (data available when required) and link stability (network links always accessible).

IPFS – InterPlanetary File System (Juan Benet)

  • Vision: a decentralized World Wide Web replacing HTTP.
  • Uses Kademlia DHT (storage) and Merkle DAG (searching).
  • Incentive: Filecoin pays nodes that store data, using the BitSwap mechanism (simple ledger of bytes sent/received).
  • Git-based versioning for structure and control.

Other storage options

Project Idea
Ethereum Swarm Decentralized storage for Ethereum Web 3.0
Storj Paid P2P cloud storage
Maidsafe SAFE network – decentralized web from users' unused resources
BigChainDB Scalable, fast, linearly scalable decentralized database; complements Ethereum and IPFS

2.2 Communication

Problem

  • The original vision of the Internet was a decentralized system, but control has shifted to big players (Google, Amazon, eBay).
  • Services like e-mail and online storage are controlled by providers; users trust them, and even passwords are stored on third-party systems.
  • Internet access depends on ISPs, which act as central hubs – if an ISP is shut down (political or other reasons), no communication is possible.
  • E-mail is decentralized at its core, but people choose free centralized services – paid for with their personal data.

Solution – Mesh networks

  • Nodes talk directly to each other without a central hub such as an ISP.
  • Example: FireChat – iPhone users communicate peer-to-peer without an Internet connection.
  • Ethereum's Whisper protocol – decentralized, encrypted P2P messaging.
  • Goal: a network that no one can shut down for political or censorship reasons (important where the Internet is censored).

2.3 Computation (computing power)

  • Decentralization of processing is achieved by blockchains like Ethereum, where smart contracts with embedded business logic run on the network.
  • Other platforms (EOS, Tezos) provide similar processing layers.
  • Blockchain therefore acts as the decentralized processing layer; it can also store data, but that affects speed and capacity → large data goes to IPFS/BigChainDB.

2.4 Identity and Wealth (top layer)

  • Traditionally centralized (banks, ID providers).
  • bitAuth and OpenID provide authentication/identification with varying degrees of decentralization and security.
  • Zooko's triangle: a naming system should be secure, decentralized and meaningful to humans – normally only two are possible at once; Namecoin solved it with blockchain.
  • Challenge: users must store and maintain private keys securely – loss of keys = loss of identity/wealth.

2.5 Summary table

Element Centralized today Decentralized alternative
Storage Cloud servers, databases DHT, IPFS + Filecoin, Swarm, Storj, Maidsafe, BigChainDB
Communication ISPs, e-mail providers Mesh networks (FireChat), Whisper
Computation Application servers Ethereum / EOS / Tezos smart contracts
Identity & wealth Banks, ID providers bitAuth, OpenID, Namecoin, crypto wallets

2.6 Limitations

  • Decentralization may not be appropriate for every scenario – reputable centralized services (Google/Microsoft e-mail) often work better than self-hosted servers.
  • Key management, performance and usability challenges remain.
3Conclusion / Summary
  • A blockchain alone is not enough – full decentralization requires the surrounding ecosystem to be decentralized.
  • Storage → DHT/IPFS/Swarm/BigChainDB; Communication → mesh networks/Whisper; Computation → Ethereum smart contracts; Identity & Wealth → bitAuth, OpenID, Namecoin.
  • Only when all layers are decentralized does the system have no single point of control or failure – though centralization may still be preferable in some cases.

4Identify the different entity in decentralized organization.16M
1Introduction

Decentralization is an old idea in management – distributing authority from one centre to the peripheries. With blockchain, it is now possible to build software versions of traditional physical organizations. These decentralized entities exist as code (smart contracts) on a blockchain, run in a peer-to-peer network, and interact according to the rules written in that code.

The different entities in a decentralized organization are: Smart contracts → Autonomous agents → DO → DAO → DAC → DAS → DApps.

Key point: The entities differ mainly in how autonomous they are (human input vs fully automatic), whether they make profit, and their scale (one organization vs a whole society).

2Content

2.1 Smart contract

  • A small decentralized program with business logic and a limited amount of data.
  • Resides on the blockchain and executes business logic when specific criteria are met.
  • Does not strictly need a blockchain, but blockchain is becoming the standard decentralized execution platform because of its security.
  • Actors use smart contracts, or they run autonomously on behalf of participants.

2.2 Autonomous Agent (AA)

  • An artificially intelligent software entity that acts on behalf of its owner to achieve goals with no or minimal intervention from the owner.
  • Example: an agent commissioned by a law-enforcement agency or regulator embedded in a DAO to ensure legal compliance.

2.3 Decentralized Organization (DO)

  • Software programs on a blockchain based on real human organizations with people and protocols.
  • Once the DO (one or more smart contracts) is added to the blockchain, it becomes decentralized and parties interact based on the code.
  • Relies on human input to execute business logic → not autonomous.

2.4 Decentralized Autonomous Organization (DAO)

  • A computer program on the blockchain with governance and business-logic rules embedded.
  • DAO vs DO: DAOs are autonomous – fully automated with AI logic; DOs need human input.
  • Code is the governing entity, not humans or paper contracts.
  • Introduced first on Ethereum.

Roles in a DAO

Role Function
Token holders (participants) Fund the DAO and vote on proposals
Curator (human) Maintains the code, evaluates proposals for the community
Contractors Hired externally if enough token-holder input is received

The DAO case study

  • Opened a debate on security, code quality and the need for thorough testing of smart contracts; academia works on formal verification.
  • DAOs currently have no legal status; they can run in any jurisdiction, raising questions for legal systems.

2.5 Decentralized Autonomous Corporation (DAC)

  • A smaller subset of DAOs.
  • DAC vs DAO: DAOs are usually non-profit; DACs make money via shares offered to participants and paying dividends.
  • Runs a business automatically without human intervention, based on programmed logic.

  • Entire societies function on a blockchain using multiple complex smart contracts and a combination of DAOs and DApps.

5Describe the generic elements of a block chain.16M
1Introduction

A blockchain is a peer-to-peer distributed ledger that is cryptographically secure, append-only, immutable and updatable only through consensus. Technically it can be described as a data structure – a linked list that uses hash pointers instead of normal pointers.

Whatever the platform – Bitcoin, Ethereum or Hyperledger – a blockchain is assembled from a common set of generic elements. Understanding them is the foundation for every other topic in the subject.

Key point: Nine generic elements – Address, Transaction, Block, P2P network, Scripting language, Virtual machine, State machine, Nodes, Smart contracts.

2Content

2.1 Addresses

  • Unique identifiers used in transactions to denote senders and recipients.
  • An address is a public key or derived from a public key (e.g. Bitcoin: hash of public key).
  • Addresses can be reused, but in practice users generate a new address for each transaction to avoid linking transactions to the common owner.
  • Bitcoin is a pseudonymous system: users are not directly identifiable, though research shows de-anonymization is possible.

2.2 Transaction

  • The fundamental unit of a blockchain.
  • Represents a transfer of value from one address to another.
  • Signed with the sender's private key; verified by nodes.

2.3 Block

  • Composed of multiple transactions plus elements such as the previous block hash (hash pointer), timestamp and nonce.
  • Its size varies with blockchain type and design.
  • A genesis block is the first block, hard-coded when the chain starts; it has no previous hash.

2.4 Peer-to-peer network

  • A network topology in which all peers can communicate with each other and send/receive messages.
  • No central server; transactions and blocks are spread by gossip (flooding).

2.5 Scripting or programming language

  • Transaction scripts are predefined sets of commands for nodes to transfer tokens and perform other functions.
  • A Turing-complete language is desirable, but its security is an issue.
  • Bitcoin Script is deliberately limited (no loops).

2.6 Virtual machine

  • An extension of the transaction script; allows Turing-complete code (smart contracts) to run on the blockchain.
  • Not available on all blockchains. Examples: Ethereum Virtual Machine (EVM), Chain Virtual Machine (CVM).

2.7 State machine

  • A blockchain can be viewed as a state-transition mechanism: the state moves from initial to next and finally to a final form as a result of transaction execution and validation by nodes.

2.8 Nodes

  • Perform functions depending on their role: propose and validate transactions, perform mining to facilitate consensus and secure the chain, by following a consensus protocol.
  • Other roles: simple payment verification (SPV), validators, etc.
Node type Role
Full node Stores whole chain, validates everything
Mining node Creates blocks, solves PoW
SPV / light node Verifies payments with block headers
Validator Votes/validates in permissioned chains

2.9 Smart contracts

  • Programs running on top of the blockchain that encapsulate business logic executed when conditions are met.
  • Not on all blockchains but increasingly desirable for flexibility and power.

2.10 Layered (network) view

  • Internet → P2P network → Transactions → Blocks → Consensus → State machine → Applications (smart contracts) → Users/Nodes.

2.11 How the elements work together – example

  1. Alice (address A) creates a transaction sending 1 coin to Bob (address B) and signs it.
  2. It is spread through the P2P network to nodes.
  3. Nodes run the script/VM to validate it.
  4. A miner packs it into a block with the previous hash, timestamp and nonce.
  5. The block is added to the chain → the state machine moves to a new state (A −1, B +1).
  6. If B is a smart contract, its code executes automatically.
3Conclusion / Summary
  • Addresses identify parties; transactions move value; blocks bundle transactions and link by hash pointers; the P2P network and nodes distribute and validate everything; scripts, virtual machines and smart contracts add programmability; and the state-machine view ties it all into a single evolving ledger.
  • These nine generic elements are present, in some form, in every blockchain platform.

8With an example, illustrate the concept of Consensus and the types of algorithms used to implement it.16M
1Introduction

Consensus is a process of agreement between distrusting nodes on a final state of data. In a client-server system agreement is trivial, but in a distributed system with many independent nodes – some of which may crash or act maliciously – reaching distributed consensus is a fundamental problem.

The classic illustration is the Byzantine Generals problem. Blockchain solves it with consensus algorithms, which are grouped into BFT-based, leader-based and proof-based types.

Key point: Consensus gives a blockchain its single version of truth without any central authority.

2Content

2.1 Why consensus is needed

  • Every node keeps its own copy of the ledger.
  • Transactions arrive in different orders at different nodes; some nodes may be faulty or Byzantine.
  • Without consensus, nodes would disagree → double spending, forks, no trust.
  • Consistency is achieved through state machine replication – all honest nodes apply the same transactions in the same order.

2.2 Example 1 – The Byzantine Generals problem

  • Generals = nodes, traitors = Byzantine (faulty/malicious) nodes, messenger = communication channel.
  • The loyal generals must agree on the same plan (attack/retreat) even though traitors send conflicting messages.
  • PBFT solves it with rounds of voting (majority of honest votes wins); it needs n ≥ 3f + 1 generals to tolerate f traitors.
  • Bitcoin's PoW solves it in an open network: the chain with the most accumulated work is accepted – a traitor would need more than 50 % of computing power.

2.3 Example 2 – Consensus in a Bitcoin payment

  1. Alice signs a transaction paying Bob 1 BTC and broadcasts it.
  2. Every node checks it (valid signature, coins not already spent).
  3. Miners compete to solve the PoW puzzle: H(N ‖ P_hash ‖ Tx ‖ … ‖ Tx) < Target.
  4. The winner broadcasts the block; others verify it and build on top of it.
  5. If two blocks appear at once, nodes follow the longest (most-work) chain; the other becomes orphaned.
  6. After ~6 confirmations, all nodes agree the payment is final.

2.4 Requirements of a consensus mechanism

Requirement Description
Agreement All honest nodes decide on the same value
Termination All honest nodes eventually reach a decision
Validity Agreed value was proposed by at least one honest node
Fault tolerance Works with faulty/malicious nodes present
Integrity Each node decides only once per cycle

2.5 Types of consensus algorithms

A. Byzantine fault tolerance-based (traditional rounds of votes; permissioned; fast, less scalable)

  • PBFT – state-machine replication; phases pre-prepare, prepare, commit; used in Hyperledger Fabric.
  • Federated Byzantine Agreement – nodes trust a group of public peers (quorum slices); Stellar.

B. Leader-based (classical distributed systems)

  • Paxos – nodes take roles Proposer, Acceptor, Learner; proposer suggests a value, acceptors vote, learners learn the chosen value.
  • RAFT – nodes are Follower, Candidate or Leader; a candidate becomes leader by majority vote and replicates the log to followers.

C. Proof-based / Nakamoto (leader chosen by proof; permissionless; scalable but slow)

1Introduction

A hash function compresses a message of any length into a fixed-length digest. SHA-256 (Secure Hash Algorithm 256, member of the SHA-2 family designed by the NSA and standardized by NIST) produces a 256-bit (32-byte) digest.

It is the most important hash function in blockchain:

  • Bitcoin Proof of Work uses double SHA-256 of the block header.
  • Block linking (previous block hash), Merkle roots, transaction IDs and address generation (SHA-256 then RIPEMD-160) all rely on it.

SHA-256 follows the Merkle–Damgård construction: the message is padded, split into 512-bit blocks, and each block is fed through a compression function together with the previous intermediate hash.

Key point: Input any length → 512-bit blocks → 64 rounds per block → 256-bit output.

2Content

2.1 Properties required of SHA-256

Property Meaning
Pre-image resistance (one-way) Given h(x) = y, it is infeasible to find x
Second pre-image resistance (weak collision) Given x and h(x), infeasible to find another m with h(m) = h(x)
Collision resistance (strong collision) Infeasible to find any two different inputs with the same hash

2.2 High-level overview

The algorithm has two phases – Pre-processing and Hash computation.

2.3 Phase A – Pre-processing

Step 1 – Padding the message

  • The message is padded so that its length becomes a multiple of 512 bits.
  • Append a single '1' bit, then '0' bits, leaving the last 64 bits to store the original message length.
  • Example: "abc" (24 bits) → 24 + 1 + 423 zeros + 64-bit length = 512 bits (one block).

Step 2 – Parsing the message

  • The padded message is divided into N equal 512-bit blocks M⁽¹⁾, M⁽²⁾ … M⁽ᴺ⁾.
  • Each block is viewed as sixteen 32-bit words.

Step 3 – Setting the initial hash value H⁽⁰⁾

  • Eight 32-bit words a, b, c, d, e, f, g, h.
  • Obtained from the first 32 bits of the fractional parts of the square roots of the first eight prime numbers (2, 3, 5, 7, 11, 13, 17, 19).
  • These "nothing-up-my-sleeve" numbers give confidence that no backdoor exists.
  • Similarly, the 64 round constants Kₜ come from the cube roots of the first 64 primes.

2.4 Phase B – Hash computation

Step 4 – Prepare the message schedule (Wₜ)

  • W₀ … W₁₅ = the sixteen 32-bit words of the block.
  • W₁₆ … W₆₃ are derived: Wₜ = σ₁(Wₜ₋₂) + Wₜ₋₇ + σ₀(Wₜ₋₁₅) + Wₜ₋₁₆ (mod 2³²).

Step 5 – Initialise eight working variables a … h with the current hash value H⁽ⁱ⁻¹⁾.

Step 6 – 64 rounds of the compression function Each round uses slightly different constants so that no two rounds are the same:

  • T1 = h + Σ₁(e) + Ch(e, f, g) + Kₜ + Wₜ
  • T2 = Σ₀(a) + Maj(a, b, c)
  • h = g; g = f; f = e; e = d + T1; d = c; c = b; b = a; a = T1 + T2

Step 7 – Compute the intermediate hash value

  • H⁽ⁱ⁾ⱼ = H⁽ⁱ⁻¹⁾ⱼ + (working variable)ⱼ (mod 2³²), for j = a … h.

Step 8 – Output

  • After the last block, concatenate the eight 32-bit words → 256-bit message digest.

1. Non-deterministic wallets ("Just a Bunch of Keys", JBOK)

  • Keys are derived from a seed via hash functions.
  • The seed is random and represented by human-readable mnemonic code words; the phrase recovers all keys.

  • Keys stored in a tree structure: seed → master key → child keys → grandchild keys.
  • Generates private-key generation information, not keys directly.
  • Whole hierarchy recoverable from the master key → easy to maintain, highly portable.

  • Master private key derived from the hash of a memorised password.
  • Prone to password guessing / brute-force; key stretching slows attackers.

5. Paper wallets

  • Key material printed on paper (QR codes); needs physical security.
  • Generated by services such as bitcoinpaperwallet.com or bitaddress.org.

6. Hardware wallets

  • Tamper-resistant devices storing keys; can be custom-built or a secure element (SE) in NFC phones.
  • Popular: Trezor and Ledger.

7. Online wallets

  • Stored entirely online as a cloud service with a web interface.
  • Easy to use, but users must trust the provider.

8. Mobile wallets

  • Installed on smartphones; pay quickly by scanning QR codes.
  • Examples: breadwallet, Copay, Jaxx (Android & iOS).

1Introduction

A Bitcoin transaction transfers value from one address to another. It can be as simple as paying someone or as complex as a multi-party contract. Key facts:

  • Each transaction has at least one input and one output.
  • Inputs = coins being spent (created by a previous transaction); outputs = new coins being created.
  • Coins are Unspent Transaction Outputs (UTXOs) measured in Satoshis.
  • Minting transactions (coinbase) have no input and need no signature.
  • Transactions are not encrypted – they are publicly visible on the blockchain.

How bitcoins can be spent is defined by Bitcoin Script, a simple, stack-based, non-Turing-complete language (no loops), using reverse polish notation, evaluated left to right with a LIFO stack.

Key point: Every output is locked by a ScriptPubKey; the spender unlocks it with a ScriptSig. The type of transaction = the type of locking script.

  • Verification – by executing the scripts.

5Illustrate the various steps involved in Elliptic Curve Digital Signature Algorithm.16M
1Introduction

A digital signature proves who created a message and that it was not altered. ECDSA – Elliptic Curve Digital Signature Algorithm – is a DSA based on elliptic curves; it relies on modular arithmetic and the discrete logarithm problem on elliptic curves.

ECDSA is used on the Bitcoin and Ethereum platforms to validate messages (transactions) and to provide data integrity, authentication and non-repudiation. Its algorithm has three steps: 1. Key generation · 2. Signing · 3. Verifying.

Key point: Smaller keys, same security as RSA – 256-bit ECC ≈ 3072-bit RSA.

2Content

2.1 Elliptic-curve background

  • Curve over a prime field: y² = x³ + ax + b (mod p), with 4a³ + 27b² ≠ 0.
  • Points on the curve form a cyclic group under point addition; a generator (base point) G has prime order n (n·G = point at infinity O).
  • Point addition P + Q and point doubling 2P = P + P:

Addition: λ = (y₂ − y₁)/(x₂ − x₁) mod p Doubling: λ = (3x₁² + a)/(2y₁) mod p x₃ = λ² − x₁ − x₂ mod p y₃ = λ(x₁ − x₃) − y₁ mod p

  • Scalar multiplication d·G = G + G + … (d times), done efficiently with double-and-add.
  • ECDLP: given Q = d·G, finding d is computationally infeasible → security of the private key.

2.2 Step 1 – Key generation

  1. Agree on domain parameters: curve E (p, a, b), base point G, order n (Bitcoin uses secp256k1).
  2. Choose a random integer d with 0 < d < n → private key.
  3. Compute Q = d · G → public key (a point on the curve).
  • Public parameters: (p, a, b, G, n, Q); private: d.

2.3 Step 2 – Signing (input: message + private key → output: (r, s))

  1. Hash the message: h = hash(msg), e.g. SHA-256.
  2. Generate a secure random k (ephemeral key), 0 < k < n. k must never be reused.
  3. Compute random point R = k · G; take r = R.x mod n. If r = 0, pick a new k.
  4. Compute the signature proof s = k⁻¹ (h + d · r) mod n. If s = 0, pick a new k.
  5. Return the signature (r, s).

2.4 Step 3 – Verification (input: message, signature, public key)

  1. Check 1 ≤ r, s ≤ n − 1.
  2. Hash the message with the same function → h.
  3. Compute w = s⁻¹ mod n (modular inverse).
  4. Compute u₁ = h · w mod n and u₂ = r · w mod n.
  5. Recover the point R′ = u₁ · G + u₂ · Q.
  6. Valid if R′.x mod n = r; otherwise invalid.

2.5 Why verification works (proof)

  • s = k⁻¹(h + dr) → k = s⁻¹(h + dr) = w(h + dr)

ECDSA is a Digital Signature Algorithm based on elliptic curves. It relies on modular arithmetic and the elliptic curve discrete logarithm problem. It is used in Bitcoin and Ethereum to validate messages (transactions) and provide data integrity, authentication and non-repudiation. The algorithm has three steps: Key generation, Signing and Verification.

2Content

Elliptic curve basics

  • Curve: y² = x³ + ax + b (mod p) over a prime finite field.
  • Points form a cyclic group; operations: point addition P + Q and point doubling 2P.
  • Private key = random integer; public key = point on the curve.

Step 1 – Key generation

  1. Define curve E with modulus p, coefficients a and b, and generator (base) point G forming a cyclic group of prime order n.
  2. Choose a random integer d with 0 < d < n → private key.
  3. Compute Q = d · G → public key (a curve point). Public key tuple: (p, a, b, n, G, Q); private key: d.

Step 2 – Signing (produce (r, s))

  1. Compute message hash h = hash(msg) (e.g. SHA-256).
  2. Securely generate a random ephemeral key k, 0 < k < n (never reuse k).
  3. Compute random point R = k · G, take r = R.x mod n (if r = 0 choose new k).
  4. Compute signature proof s = k⁻¹ (h + d · r) mod n.
  5. Return the signature (r, s).

Step 3 – Verification

  1. Compute hash h of the message with the same hash function.
  2. Compute w = s⁻¹ mod n.
  3. Compute u₁ = h · w mod n and u₂ = r · w mod n.
  4. Recover the point R′ = u₁ · G + u₂ · Q.
  5. Signature is valid if R′.x mod n = r, otherwise invalid.

Why it works

R′ = u₁G + u₂Q = (h·w)G + (r·w)dG = w(h + rd)G = kG = R, since w = s⁻¹ = k(h + dr)⁻¹.

Worked mini-example

  • Bitcoin uses curve secp256k1 with 256-bit private keys.
  • Ethereum signature fields (v, r, s): ECDSASIGN(Message, PrivateKey) = (V, R, S); precompiled ECRECOVER recovers the public key.

2.4 Bloom filters

  • A bit vector used for probabilistic membership testing.
  • False positives possible, false negatives impossible.
  • Add element: hash it several times, set the indexed bits to 1. Test: same hashes, check bits.
  • Hash functions must be fast and uniform: fnv, murmur, Jenkins (not SHA-1).
  • Strict filter → precise but may reveal the user's addresses (privacy risk); loose filter → more privacy, more data.
  • BIP37 messages: filterload (set filter), filteradd (add element), filterclear (remove filter).
  • Merkle block = header + some hashes + list of 1-bit flags + transaction count.

1Explain the four stages involved in encrypting plaintext using AES.2M

AES works on a 4 × 4 byte state array for 10/12/14 rounds (128/192/256-bit key). Each round has four stages:

  1. AddRoundKey – state is XORed with a round subkey derived from the master key.
  2. SubBytes – each byte is replaced using a lookup table (S-box).
  3. ShiftRows – every row except the first is shifted left cyclically and incrementally.
  4. MixColumns – bytes of each column are mixed linearly.

In the final round, MixColumns is replaced by AddRoundKey.

2.4 Working – transaction flow

  4. Orderer orders transactions into blocks (consensus) and delivers them to all peers.
  5. Committing peers validate each transaction (endorsement policy, version conflicts) and commit the block; world state updated.
  6. Events notify the client application.

12b(i)Define hashing. Discuss the use of hashing in block chain technology. (8)8M
1Introduction

Hashing is the process of passing a message of any length through a hash function to produce a fixed-length digest (e.g. 256 bits). Hash functions are keyless primitives that provide data integrity and act as one-way functions.

2Content

Properties of a cryptographic hash function

  • Pre-image resistance (one-way): given h(x) = y, finding x is infeasible.
  • Second pre-image resistance: given x and h(x), finding another m with the same hash is infeasible.
  • Collision resistance: two different inputs should not hash to the same output.
  • Avalanche effect: a one-character change gives a totally different hash.
  • Fast to compute, fixed output. Families: MD5 (128), SHA-1 (160), SHA-2 (SHA-256…), SHA-3/Keccak, RIPEMD-160.

Uses of hashing in blockchain

  1. Chaining blocks – each header stores the previous block hash; changing any block breaks all later links → immutability.
  2. Proof of Work – Bitcoin miners search a nonce so that SHA256(SHA256(header)) < Target.
  3. Merkle trees – transactions hashed pair-wise to a Merkle root in the header → efficient verification (SPV).
  4. Addresses – Bitcoin address = Base58Check(RIPEMD-160(SHA-256(public key))).
  5. Digital signatures – the hash of the transaction is signed (ECDSA).
  6. Transaction IDs – double SHA-256 of transaction data.
  7. Ethereum – Keccak-256 for state, transaction and receipt tries, addresses, codeHash.
  8. DHTs / IPFS – content addressed by hash.
3Conclusion / Summary

Hashing converts any data into a fixed, unique fingerprint. In blockchain it links blocks, powers PoW, builds Merkle trees, creates addresses and secures signatures – the foundation of immutability and integrity.

4Revision Remarks
  • 3 properties: pre-image, second pre-image, collision resistance (+ avalanche).
  • Bitcoin: double SHA-256 (PoW, tx IDs); RIPEMD-160 (addresses). Ethereum: Keccak-256.
